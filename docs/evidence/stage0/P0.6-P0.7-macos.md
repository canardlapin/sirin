## What the probe is

The shim lives in `src/main/resources/scala-native/`:
- `sirin_mailbox.c` is a bounded native mailbox: one mutex, condition
  variables, inline 64-byte slots.
  - The message is copied at delivery, so no allocation happens on the
    producer thread.
  - Consumers are addressed by handle (slot plus 16-bit generation). Statuses
    are `OK`, `FULL`, `CLOSED`, `TOO_LARGE`, and `STALE`.
  - The wake function is called outside the lock and is coalesced to one wake
    per empty → pending transition.
- `sirin_guard.c` is the thread-identity guard. Scala-created threads mark
  themselves. `sirin_require_scala_thread` aborts unless the thread is both
  marked and registered with the GC. Registration is read from immix's
  thread-local `currentMutatorThread`, an internal symbol used in the probe
  only.
- `sirin_foreign.c` holds the raw-pthread producers and the re-entry-shape
  delivery. No `CFuncPtr` is reachable from these threads.
- `sirin_threads_shim.c` holds the SDL glue (user events, the
  `SDL_PushEvent` wake, an event-watch counter), a C watchdog that aborts if
  any heartbeat stalls, the re-entry trampolines, and the cost probes.

The Scala side is `ThreadsProbe.scala`, `Stress.scala` and `Consumer.scala`.
Every result line starts with `RESULT`, and any failed criterion exits
non-zero.

## P0.6 soak: workers allocate while main waits in SDL

**Setup.**
- Four Scala allocator threads allocate 16–1039-byte arrays, lists, and
  strings. Each keeps a rotating ring of 2,048 survivors, a bounded live set
  of about 4 MB.
- Each worker pushes a timestamped SDL user event every 1 ms.
- Main calls `SDL_Init(VIDEO)`, creates a hidden window, and loops in
  `@blocking SDL_WaitEventTimeout(…, 100)`. It records push → receipt
  latency.
- A ticker thread sleeps 1 ms in a loop and records oversleep. Oversleep
  bounds the stop-the-world pause, including the time to reach a safepoint.
- `GC_STATS_FILE` records each collection's mark+nullify+sweep time. That
  figure excludes safepoint synchronization.
- The watchdog stall limit is 10 s.

| 600 s run | debug | release-fast |
|---|---|---|
| Deadlock / watchdog | none | none |
| Events pushed = received | 928,765 = 928,765 | 2,213,050 = 2,213,050 |
| Allocated | 1,083 GiB, 1.73 × 10⁹ iterations | 6,241 GiB, 9.98 × 10⁹ iterations |
| Collections | 15,747 | 31,581 |
| GC mean (stats counter) | 17.9 ms | 0.75 ms |
| GC max (stats file) | 1,269.8 ms (447 > 50 ms) | 184.9 ms (3 > 50 ms, 7 > 20 ms) |
| Latency p50 / p99 / p99.9 / max | 0.05 / 8.37 / 89.9 / **952** ms | 0.04 / 0.33 / 4.56 / **197** ms |
| Ticker max oversleep | 1,307.6 ms (687 > 50 ms) | 227.7 ms (18 > 50 ms) |
| RSS start → end | 31.5 → 255 MB | 33.9 → 753 MB |
| Result | `no_deadlock` PASS, `all_events_received` PASS, `latency_max_below_50ms` **FAIL**, `ticker_max_below_50ms` **FAIL** | the same |

**Finding: the immix heap grows without bound under concurrent allocation.**

The RSS figures above track `scalanative_GC_get_used_heapsize`, which is the
committed heap. These release-fast runs had no SDL pushes, so SDL is ruled
out:

| Allocating threads | Heap after 60 s | Note |
|---|---|---|
| 1 | 8.5 MB, flat (40 s run: also 8.5 MB) | — |
| 2 | 83 MB | — |
| 4 | 225 MB, then 321 MB at 120 s | — |
| 4, with `GC_MAXIMUM_HEAP_SIZE=128M` | — | aborted: `[ScalaNative GC\|Error] Out of heap space cannot allocate more objects` |

The live set is about 4 MB, so this is not the workload's own memory. The
pause tail grows with the heap. The probe does not establish the root cause.
A plausible candidate is immix's round-robin recycling of blocks to every
mutator thread (`Heap_Recycle`/`NextMutatorThread`) combined with
`Heap_shouldGrow`. The roadmap requires escalating this to the Scala Native
maintainers with a minimal reproducer: `soak 60 2 0` against `soak 60 1 0`.

A second observation pointed the same way. An earlier P0.7 run kept a
growing `HashSet` of dead handles (156,000 entries) on the main thread
while four workers allocated. The heap grew to 553 MB and the mean pause rose
from 7 ms to 30 ms. Replacing it with a fixed array returned the heap to
39 MB.

Debug mode is far slower than release-fast (17.9 ms against 0.75 ms mean).
The load on the shared machine inflates every tail figure. Even so, the
release-fast GC's own stats file records three collections above 50 ms
(max 185 ms), and that figure contains no safepoint wait. **The 50 ms
criterion is not met.** Rerun on an idle machine after the heap-growth
issue is resolved, and with commix as a comparison.

## P0.6 re-entry: a Scala `CFuncPtr` called from C inside an extern

**Setup.**
- `sirin_reenter_{blocking,plain}` are the same C function, declared once
  as `@blocking` and once plain.
- For each call, the C function invokes a Scala callback through the guarded
  trampoline.
- The callback allocates 32 × 256-byte arrays that live only in its own
  frame. It then churns 2,000 small allocations and verifies the arrays'
  contents.
- Three other threads allocate and call `System.gc()` every 50,000
  iterations.
- The C side reads the immix thread state before each callback, and the
  callback reads it again inside.

| Run (seconds, callbacks per call) | Outcome | Thread state inside the callback |
|---|---|---|
| debug, `@blocking`, 20 s, 50/call | completed, 0 corrupt bytes | 3,970 Unmanaged, 19,980 Managed (of 23,950) |
| debug, `@blocking`, 60 s, 1/call | **1 of 3 runs crashed:** `ScalaNative: Unhandled signal 11, si_addr=0x10`. Two completed with 0 corrupt bytes. | 100% Unmanaged (107,712 of 107,712) |
| release-fast, `@blocking`, 30 s, 1/call | **4 of 4 runs failed:** `java.lang.ArrayIndexOutOfBoundsException: Index 0 (23, 30) out of bounds for length 0` in `Reentry.body`. An array referenced from the callback frame was reclaimed or zeroed. | — |
| debug, plain, 20 s and 60 s | completed, 0 corrupt bytes | 100% Managed |
| release-fast, plain, 30 s, 1/call | 2 of 2 completed (272,988 and 241,835 callbacks), 0 corrupt bytes | 100% Managed |

**Finding: re-entry inside `@blocking` is unsafe on 0.5.12.** The
`CFuncPtr` forwarder does not switch the thread back to Managed. The
callback therefore runs Scala code while the GC treats the thread as parked,
with a stack top recorded at the extern's entry. Frames below that point,
the callback's own, are not scanned, so the objects they hold can be
reclaimed. There is a second effect. Once a collection happens inside the
callback, `Synchronizer_yield`/`_release` leave the thread Managed for the
rest of the native call. That explains the 50/call split above, and it means
any later blocking inside that call stalls the GC.

**Rule recorded in VISION §6.1:** Scala callbacks are allowed only from
plain externs, and those externs must not block. No engine code may depend
on `@blocking` re-entry.

## P0.6 cost of strict (non-`@blocking`) semantics

Measured with `cost`:

| | debug | release-fast |
|---|---|---|
| no-op plain extern | 4.61 ns/call | 2.08 ns/call |
| no-op `@blocking` extern | 188.98 ns/call | 131.53 ns/call |
| **`@blocking` overhead** | **184 ns/call** | **129 ns/call** |
| Main in a 200 ms native sleep, `@blocking`: allocation rate / ticker max | 2.08 M it/s / 56.2 ms | 10.1 M it/s / 12.8 ms |
| Main in a 200 ms native sleep, plain: allocation rate / ticker max | 0.118 M it/s / **210.9 ms** (10 > 50 ms) | 0.092 M it/s / **222.6 ms** (10 > 50 ms) |

The overhead is the register capture and the atomic state transitions. A
plain extern that blocks stalls every allocating thread for its whole
duration, which dropped worker throughput about 18× (debug) and 110×
(release-fast). So `@blocking` stays mandatory for blocking calls, and it is
too costly for hot, short calls.

## P0.7: foreign-thread entry (hard gate)

**Setup.** All producers are raw pthreads created in C. Each producer checks
on entry that it is unmarked and unknown to the GC (`gc_state == -1`), and
counts violations. Main is the only consumer. It drains on SDL wake events
and verifies every message:
- the payload checksum,
- the producer and sequence fields,
- per-producer FIFO order: contiguous in (a), (b) and (d), strictly
  increasing in (c).

Four Scala threads allocate heavily throughout.

`foreign 1000000` passes every check in both builds, with 0 failures.
Numbers below are from debug; release-fast numbers follow in parentheses.

| Case | Result |
|---|---|
| (a) 8 foreign producers × 125,000, blocking on full (capacity 1024) | 1,000,000 delivered = drained = received. Order and payload intact. All 8 producers confirmed foreign. 359 collections ran during the case. 3.3 s, or 0.17 s release-fast. **PASS** |
| (b) Close while producers are active: 4 producers per round (blocking and non-blocking rounds alternate), close after 0–20 ms, and one round in three destroys with messages queued | 25 rounds (20 release-fast); 1,236,901 OK deliveries, 1.56 × 10⁷ attempts. Every producer ended with a clean `CLOSED` (100 of 100). For every round, OK = drained + discarded at destroy. Mailboxes freed (live count 0). RSS 74.8 → 79.4 MB across the rounds. **PASS** |
| (c) Unregister while deliveries are in flight: 4 producers × 250,000 over 4 handle slots, with main rotating one handle per pass | 85,895 rotations. 973,553 OK and 26,447 rejected `STALE` (= 10⁶ attempts). 241,503 dropped at drain for stale handles. Zero deliveries to an unregistered handle, and no handle reissued. **PASS** |
| (d) Deliveries from a native call stack that started in Scala: 500 `@blocking` calls, each delivering 1,000 synchronously through a C callback chain on the calling thread, then 1,000 from a fresh foreign pthread while the caller waits inside the call | 1,000,000 delivered and drained, in order. 500 of 500 inner threads confirmed foreign. **PASS** |

Further checks, in both builds:
- **Guard.** A raw pthread reports `marked=0 gc_state=-1`, and main reports
  `marked=1 gc_state=0`. A foreign thread entering the guarded trampoline
  aborts:
  - in a forked child: SIGABRT, status 6;
  - in process: `guard-abort` prints `sirin: FATAL: Scala entry
    'sirin_invoke_guarded' reached on a foreign thread (marked=0,
    gc-registered=0); aborting` and exits 134.
- The guarded-entry counter did not move during cases (a)–(d), so no Scala
  callback was entered.
- **SDL event watches.** An SDL event watch saw user events on 20,296
  foreign threads and 500 Scala threads, and 0 others. SDL runs watches
  synchronously inside `SDL_PushEvent` on the pushing thread, so a Scala
  event watch or filter would run Scala on a foreign thread. The design
  rule is now in VISION §6.1.
- `SDL_PushEvent` failures: 0.

**Finding: generation wrap.** The first version wrapped the 16-bit
generation. The pure-C harness rotated one slot more than 65,535 times (2.2
million rotations in total), so a stale handle could become live again
(ABA). The mailbox now retires an exhausted slot instead of wrapping it, and
a unit test covers this. The engine should use wider handles; VISION §6.1
records this.

### ThreadSanitizer

- **Full Scala Native binary** (`-Dsirin.sanitize=thread`). This links and
  runs: `foreign 100000` passes every case, and `reentry blocking` completes.
  - TSan reported **one race, inside the Scala Native runtime**:
    `__scalanative_loadModule` / `__scalanative_startAndWaitForModuleInitialization`,
    on the lazy load of `MainThreadShutdownContext` when two worker threads
    terminate together.
  - It reported **none in the shim**. Exit 134 is Darwin's
    `abort_on_error` acting on that report.
  - **Coverage limit:** Scala-compiled code is not instrumented. Disassembly
    of `Consumer.check` shows no `__tsan_read*` or `__tsan_write*` calls,
    while the shim's `sirin_mbox_drain` begins with `___tsan_func_entry`.
    This run therefore checks the C side only, and it did not detect the
    `@blocking` re-entry corruption.
- **Adapter: a pure-C harness** (`probes/threads/tsan/`). It compiles the
  exact `sirin_mailbox.c`, `sirin_guard.c` and `sirin_foreign.c` with
  `-fsanitize=thread -Werror` and `halt_on_error=1`, using a C consumer
  thread.
  - At 10⁶ per case, (a)–(d) all pass with no TSan reports:
    - (b) ran 875 shutdown rounds;
    - (c) ran 147,453 rotations, with 120,149 rejected stale and 85,631
      dropped at drain.
  - A deliberately racy control program was reported by the same clang,
    which shows the sanitizer is active.

### Unit tests

`sbt probeThreads/test` runs `MailboxSuite`, 13 tests, all passing:
- `sirin_msg` layout matches C;
- bounded capacity, and a timed wait that expires;
- FIFO across a drain limit;
- copy-on-deliver ownership, and oversize/empty payloads;
- close semantics, including refusing to destroy an open mailbox;
- close releases a blocked foreign producer with `CLOSED`;
- stale handles: rejected at delivery, dropped at drain, never reissued;
- an exhausted generation retires its slot;
- wake coalescing;
- raw-pthread identity;
- the forked guard abort;
- the guarded call on a Scala thread;
- checksum determinism.

## Not covered here

- AccessKit's threads and SDL's internal threads calling the shim. Only C
  pthreads were exercised. AccessKit is not integrated yet.
- The wgpu `WaitAny` callback path. Its shim already records results only.
- An idle-machine rerun of the soak. The root cause of the immix heap
  growth. Commix and Boehm comparisons. Release-full and LTO builds.
- x64 Linux and Windows (S-0.4).
- Leak checking beyond mailbox accounting, the live-mailbox count, and RSS
  across shutdown rounds. No `leaks`/ASan run was made.

```sh

B=probes/threads/target/scala-3.7.4/sirin-probe-threads

awk -F, 'NR>1{t=$1+$2+$3; if(t>m)m=t} END{print m/1e6 " ms"}' /tmp/gc.csv
$B soak 60 1 0; $B soak 60 2 0                       # heap growth: 1 vs 2 allocators, no SDL pushes
$B reentry blocking 30 1; $B reentry plain 30 1      # re-entry hazard vs control
$B cost
$B foreign 1000000                                   # quick mode: $B foreign 10000
$B guard-abort; echo $?                              # expect 134

sbt -Dsirin.sanitize=thread probeThreads/nativeLink  # then: $B foreign 100000
```

## Main-session verification and follow-up (2026-10-27, 12:36–12:46)

This was run on the same shared machine at load 9–16, after the merge
(`c1ce4e2`), using `probes/threads/target/scala-3.7.4/sirin-probe-threads`.
A new build switch, `-Dsirin.gc=commix|boehm|none`, selects the collector.

| Build | Command | Result |
|---|---|---|
| debug, immix | `soak 30 1 0` | heap 8.5 MB |
| debug, immix | `soak 30 2 0` | heap 30.1 MB. Growth with two allocating threads reproduced. |
| debug, immix, `GC_MAXIMUM_HEAP_SIZE=128M` | `soak 60 4 0` | Survived, heap 84.1 MB at 60 s. Debug allocates more slowly, so it did not reach the cap. |
| release-fast, immix, `GC_MAXIMUM_HEAP_SIZE=128M` | `soak 60 4 0` | **Out of heap space.** The agent's result is reproduced. |
| debug, commix | `soak 30 {1,2,4} 0` | heap 153.8 / 185.6 / 312.1 MB. Commix grows even with one thread. |
| debug, commix, `GC_MAXIMUM_HEAP_SIZE=128M` | `soak 60 4 0` | **Out of heap space** |
| release-fast, immix | `soak 40 1 0`, run 3 times, with and without the cap | **3 of 3 aborted on a safepoint stall** (details below) |

**The safepoint stall is a new failure.** It is not the heap growth.
- The GC logged "Waiting for 1 thread(s) to reach safepoint (10.0s
  elapsed) … state=Managed". The probe watchdog then aborted with
  "slot 0 made no progress for 10000 ms" (exit 134).
- It needs release-fast, a single allocating worker, and no SDL pushes. The
  main thread then spends its time in `@blocking SDL_WaitEventTimeout(100)`.
- It does not appear in debug, or in the agent's 4-worker release-fast soak
  with pushes.
- The stuck thread was in `Managed` state, so it was running Scala code,
  not blocked in native code. Which thread it was is not established.

**Conclusions:**
- P0.6 stays **blocked**. Both failures are reproducible on the pinned
  0.5.12 runtime:
  - committed-heap growth under concurrent allocation, ending in OOM
    under a cap (seen with both immix and commix),
  - a release-mode safepoint stall.
- Boehm was not tried, because it needs an external libgc.
- The next step is minimal standalone reproductions (no SDL, no Sirin code)
  for the Scala Native issue tracker. Run them again on an idle machine
  before filing.

## New-machine follow-up

The [standalone macOS reproduction](P0.6-standalone-macos.md) isolates the
allocation OOM without Sirin or SDL on a second machine. It reproduces with
both trap and conditional yieldpoints. The separate safepoint stall was not
observed in the bounded rerun; P0.6 remains blocked.
