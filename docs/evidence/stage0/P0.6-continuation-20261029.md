# P0.6 continuation — independently reproduced safepoint stall

On 2026-10-29 the historical single-worker safepoint failure reproduced with
both the preserved stock Scala Native 0.5.12 binaries and the preserved full
upstream `fa4a9e6ac9dab73ab4d476d6cc8c0cdc422c25f7` evaluation binaries.
The upstream candidate's earlier finite heap-growth result does not qualify
safepoint progress. No Sirin runtime pin, GC policy or kernel semantics changed.

| Workload, three attempts each | Stock 0.5.12 | Pinned upstream |
|---|---:|---:|
| Sirin threading probe, `soak 40 1 0` | 2 safepoint/watchdog aborts; 1 completed | 1 safepoint/watchdog abort; 2 completed |
| Standalone Scala Native, `40 1 2048 true` | 1 safepoint/GC-timeout abort; 2 completed | 2 safepoint/GC-timeout aborts; 1 completed |

All twelve attempts are retained. Executables were SHA-256 verified against
prior receipts before execution; these are the same preserved binaries, not
new builds. Every run used a 128 MiB heap cap, 15 s GC synchronization timeout
and an independent 55 s process timeout. The six aborts returned signal 6;
none required external timeout. Cases ran serially within this investigation
on a shared host. These small counts are not failure-rate estimates or evidence
that either runtime is better.

The standalone program uses only Scala Native/JDK APIs plus nonblocking runtime
GC counters: one allocator, a bounded 2,048-array survivor ring, a 1 ms sleeping
ticker and a main thread sleeping 100 ms between deadline checks. It has no
SDL, Sirin, mailbox, user C code or managed callback. Its sampled heap capacity
was 8,947,712 bytes after startup in every standalone run, including failures.
Thus SDL and Sirin's shim are not necessary for this reproduced stall; the
observed failure is separate from the earlier concurrent-allocation growth case.

## Native stack evidence and limits

`standalone-pinned-w1-2/native-stall.sample.txt` was attached only **after** the
GC had already logged ten seconds waiting for a managed thread. The attach
receipt includes the pre-attach warning. It shows:

- main: `Thread.sleepNanos` -> `Synchronizer_yield` -> `sigwait`;
- allocator/collector: `Synchronizer_acquireGeneration` waiting/yielding;
- sleeping ticker: `PosixThread.sleepInterruptible` at offset +336.

The frozen binary disassembly maps that sampled ticker offset to `ldr xzr,
[x8]`, its trap-poll load. This narrows the next inspection to safepoint trap
handling/admission around sleep; it does not establish a specific lost signal,
compiler defect, missing annotation or causal patch. Profiling happened after
the stall warning and cannot explain its initial occurrence. Five other failed
runs were unprofiled.

## Separate conditional-yieldpoint comparison

After the twelve primary attempts and required test suites finished, three
additional serial trials used the preserved **stock 0.5.12 conditional-yieldpoint**
binary with the same standalone arguments and runtime limits. All three
completed without a safepoint warning, runtime abort or external timeout.
After-startup sampled heap capacity remained 8,947,712 bytes. These are a
separate three-case control; the original twelve results remain unchanged.

Conditional yieldpoints were selected when that binary was linked, not by
changing environment variables on a trap-mode executable. Its hash matches
the prior build manifest, and its recorded trap-symbol inventory is empty.
This comparison is consistent with a trap-path-specific failure in the tested
configuration, but three short completions cannot establish a remedy, a failure
rate, long-run progress or acceptable UI latency. Sirin's default is unchanged.

`testJVM` and `testNative` subsequently recorded in this receipt both pass:
299 cases each, 598 total. They ran after the primary experiments and before
the conditional controls. These default-runtime regression suites do not
qualify the failing release-fast stress configurations.
