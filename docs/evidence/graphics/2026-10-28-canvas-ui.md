## Implemented bridge and geometry

The new pure JVM/Native `graphicsUI` project (`sirin-graphics-ui`, `graphics-ui/`)
depends on core, graphics and textUI. Core and graphics remain independent of
each other and of the bridge. The root aggregation and required platform test
aliases include it. The existing isolated paragraph component additionally
depends on `graphicsUI.native` for real-font/public-element qualification.

`RecordingCanvas.record(theme, preparedText)(body)` returns a graphics Drawing
from the current core Canvas interface: fills, centered strokes, butt-capped
lines, rectangular clips, offsets, isolated opacity and resolved text. It uses
public graphics operations. Coordinates and straight-alpha colors use the same
conversion helper as the text bridge, with no device scale or premultiplication.
`Path.roundedRectangle` adds a public reusable path constructor, clamping finite
nonnegative radii to half the shorter side and falling back to rectangle paths
for zero radius/degenerate dimensions. Four cubic corners use control factor
0.5522847498307936. This is an explicit approximation, not exact circular arcs
or demonstrated browser/renderer quality at arbitrary scale.

Core by-name scopes retain one canvas handle while switching its active graphics
target. `finally` restores that target, and graphics scopes roll back their full
command range when an error escapes. Tests catch scope failures and continue
in the surrounding canvas. Text operations use an identity-transform rollback
scope to cover their complete multi-run emission. Painter order, established
clip/transform ordering, group isolation, paint alpha and relative glyph origins
remain explicit commands; pixels are not rasterized by this bridge.

All canvas operations, theme and service access check creating-Scala-thread and
lexical validity. Handles expire on both normal and failed return. Closing
clears active state, including supplied theme and inventory references. Drawing
retains command dependencies, not the recording capability or preparer. This
is not a GC/memory-retention measurement or mounted state-write enforcement.

## Preparation and paint-time text policy

`PreparedText.prepare` explicitly calls core TextServices under the existing
Committed requirement before recording. It deduplicates requests in first-use
order and accepts actual ResolvedTextLayout results. `fromResolved` accepts
explicit associations to existing real layouts, including after native closure.
Both validate exact source and requested width; conflicting duplicate keys
reject. The caller owns style meaning and native resources.

The inventory retains results, not a service/closure/native owner. The canvas's
TextServices is immutable lookup only; string convenience text uses an
infinite-width/unwrapped request. Missing requests throw TextNotPrepared instead
of preparing on demand. Wrapped text uses the corresponding prepared lookup or
an explicit resolved layout. Exact glyph objects, resolved face snapshots and
placed runs are preserved. The tests close native services before paint and
assert a counted real preparer remains at two calls after lookup/recording.

Default input limits: 1,024 entries, including duplicates, and 1,048,576 total
UTF-16 units. They check before service calls. Output admission additionally
bounds 262,144 final glyphs across distinct requests and 64 MiB of unique
requested font-file payload. Requested fallback fonts count even when unused
for painting; FontData identities deduplicate bytes. Glyphs count per distinct
request even when aliases share a layout. Failure returns no partial inventory
and closes no supplied owner. These are inventory limits, not peak allocation
or aggregate shaping-work measurements; each service layout keeps its existing
input/work budgets. No persistent cache, invalidation epoch, scheduler policy
or font discovery was introduced.

The complete [module contract](../../../graphics-ui/README.md) specifies source,
width, lifetime, rounding and scope behavior. Native services remain in the
isolated paragraph project. No new FFI, native dependency build, Rust library,
callback, foreign Scala entry or kernel semantic change was needed.
