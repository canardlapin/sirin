## Implemented semantics

`NativeParagraph.layout` and the new `NativeParagraph.wrap` share one preparation
and line-shaping engine. `TextLineLayout` owns exact glyph/face choices, global
source range, line bidi/items, line-local placements, baseline, advance/ink bounds
and issues. `ParagraphLayout.line` exposes one complete unwrapped line;
`WrappedParagraphLayout.lines` stores the same representation with vertical
`PlacedTextLine` origins. No second graphics-only text engine or core adapter
was introduced.

Wrapping candidates are the pinned ICU4X Unicode line opportunities intersected
with grapheme boundaries. Each candidate is actually shaped and measured. From
the current source start, the furthest fitting end wins. All later opportunities
are examined: contextual substitution/kerning does not justify an assumption
that measured widths are monotonic. If none fits, the first legal span is
retained. Its actual width remains visible and `hasOverflow` is true. The
requested width is finite and nonnegative, including zero. `isComplete` reports
glyph/feature coverage independently of overflow.

This retains all source whitespace/codepoints, without collapse, trimming,
justification, right-alignment, emergency grapheme breaking or inserted hyphens.
Tabs and hard separators remain unsupported in this single-paragraph component.
Soft hyphens reject explicitly until a discretionary hyphen policy exists; an
invisible selector is not treated as a successfully painted hyphen.
The distinction between Unicode opportunities and width-based selection follows
[UAX #14 revision 57](https://www.unicode.org/reports/tr14/tr14-57.html).

Paragraph bidi and script/bracket assignment still see complete source. Each
candidate applies actual line-dependent L1/L2 and projects paragraph script
assignments onto line graphemes. Bracket script context therefore survives a
wrap. X9-only graphemes use the paragraph base level for their invisible shaping
runs; their source and explicit X9 bidi records remain intact. A visible level
change inside a grapheme rejects as before.

Each line then uses the existing supplied-face/whole-atom fallback and actual
run placement. It does not slice old glyph arrays, reverse source text or
reinterpret a substring as an independent bidi paragraph. Issues from discarded
candidates do not enter the chosen layout. Width is the maximum actual line
advance and height is the sum of line heights; origins start at x=0 with
contiguous vertical placement. Ink can overhang advance bounds. Measurement and
recording consume the same stored lines, runs and positions after native closure.

## Line context at the native boundary

The existing three-argument `NativeFont.shapeRange` retains full-source context.
A four-argument overload now takes an explicit containing context range. C calls
HarfBuzz with that UTF-8 window and an item offset relative to it, sets actual
context-edge BOT/EOT flags, and rebases returned clusters to global source byte
offsets. `ShapedRun.context` retains the precise shaping window. All ranges are
validated against original codepoint boundaries and must contain the item.

Wrapped candidates use their line as context. This preserves contextual shaping
between font/script items within a line while preventing Arabic joining through
the wrap. The original source and UTF-8/UTF-16 mappings remain shared. The
[HarfBuzz buffer contract](https://harfbuzz.github.io/harfbuzz-hb-buffer.html)
is the reference for context and item offsets. No new rasterizer, Unicode table,
Rust dependency or native external artifact build was needed.

`sg_text_shape` remains an annotated `@blocking` pointer/scalar-only extern; its
additional context bounds cross no structs by value. Borrowed bytes/results end
inside the call as before. There are no Scala callbacks, foreign-created threads,
new finalizers or kernel identity/scheduling/lifetime changes. The integration
still links one ICU4X Rust library with C/C++ HarfBuzz/FreeType, without wgpu or
AccessKit. Production host/pause gates remain open.

## Bounds and practical limits

Defaults additionally admit at most **1,024 selected lines** and **4,096 candidate
evaluations**. The existing **8,192 calls / 16 MiB copied context / 262,144 attempt
glyph** shaping counters cover the complete operation, including discarded
candidates, rather than resetting per line. The **4,096 final run** limit covers
all selected lines together. Source, face, bracket and per-call native glyph
bounds are unchanged. Failures return no partial successful layout.

This prototype can do quadratic candidate work and recomputes line bidi data.
Shaping still copies the full owned source for each attempt even when HarfBuzz's
visible context is a shorter window; the byte budget conservatively charges the
full source. Candidate reuse, production latency and allocation rates remain
unqualified. Exhausting a budget is an explicit error, not permission to use an
unshaped width estimate or silently change break policy.
