# Rulings on the A-0 authoring review

**Date:** 2026-10-27.

**Status:** accepted by the project owner on 2026-10-27 with the amendments
in [the accepted package](2026-10-27-a0-recommendations.md), integrated into
VISION. The package controls where it clarifies these original rulings.

**Inputs:**
- `examples/REVIEW.md`, which raises 24 awkwardnesses and 18 open semantic
  questions,
- VISION §4, §5, and §8.

Each ruling says what the engine does. Where a ruling changes VISION, the
affected section is named. Answering the questions this way does not
discharge the A-0 exit criterion. That criterion still requires the
corpus to be rewritten against the revised skeleton and reviewed again.

## Semantic rulings (open questions Q1–Q18)

### Transactions and commands

**R1 (Q1, Q2): one scoped savepoint, `attempt`.** VISION §5.1 said "no
savepoints in v0". That changes in exactly one way:
- `txn.attempt { … }` runs its block as a nested scope inside the current
  transaction.
- A **refusal** inside the block, from `txn.require` or `refuse(reason)`,
  discards only the writes made inside the block and returns
  `Refused(reason)`. Writes made before or after the block, in the same
  transaction, stand.
- An **exception** still poisons the whole transaction. A refusal is a
  value; an exception is a defect.
- A command's `start` always runs inside an implicit `attempt`. So a
  disabled or refused dispatch returns `Refused`, does not reject the
  caller's handler, and leaves the caller's own writes in place: the
  handler can mark every field touched and still refuse the save (#15).

  Updates VISION §5.1 ("Failure is data, and rejection is explicit").

**R2 (Q11, awkwardness #4): concurrency and acceptance are separate
axes.**

| Axis | Values |
|---|---|
| **Concurrency** | `Parallel`, `Serial` (queue), `RefuseWhileRunning`, `Supersede` (cancel the older run) |
| **Acceptance** | `LatestOnly`, `Progressive`, `EveryInvocation`, `SnapshotAssociated` |

- VISION's policies become named presets:
  - `preview` = Supersede × LatestOnly,
  - `download` = Parallel × EveryInvocation,
  - `save` = **Serial** × SnapshotAssociated.
- Snapshot-associated acceptance does **not** imply serial execution. The
  `save` preset chooses serial so that revision 17's bytes can never reach
  disk after revision 18's.
- Snapshot-associated completions reconcile through a **monotonic marker**:
  a completion for revision *r* never lowers a recorded marker that is
  already above *r*.

  Updates VISION §5.4.

**R3 (Q10, awkwardness #1, #3): command status is available while the
command is being built.**
- The builder receives explicit stable read-only `CommandStatus`, including
  `running: Signal[Int]` and `lastOutcome`; no recursive initialization.
- Invocation scheduling/cancellation/delivery resources retire deterministically
  after terminal delivery. Retained outcomes are ordinary data; observations
  have scope/dispose ownership. Dropping a handle is not a cleanup event.

**R4 (Q6): revisions are per cell.**
- A cell starts at revision 0.
- Each committed write of an **unequal** value advances the revision by 1.
  An equal write does not advance it, which matches the rule that equal
  values do not propagate.
- Revisions are not global.
- Undoing back to the saved text advances the revision, so a document
  counts as dirty if dirtiness is defined by revision. An application that
  wants value-based dirtiness compares values. The framework provides both
  `revision` and `value`, and policy belongs to the application.

**R5 (Q7): effects.**
- An effect runs once at mount, with the settled initial value, after the
  mounting pass reaches `Settled`. It then runs once per committed change.
- A value that changes and changes back within one transaction publishes an
  equal snapshot, so the effect does not run.

**R6 (Q12): `Failed` is for defects.**
- Domain validation uses ordinary values (`Either`, `Validated`, or
  similar). `Failed` marks a defect, such as a derivation that threw.
- Unhandled failed bindings show a safe unavailable/error state and report it.
  Development may expose diagnostic detail; release must hide exception internals.
  Explicit fallback or retained previous content with a visible stale/error
  indication is allowed; silent release-only last-good substitution is not.
- A command whose enablement is `Failed` is disabled, and a diagnostic is
  raised.

  Updates VISION §5.1.

### Identity, structure, and focus

**R7 (Q13, awkwardness #2): component identity.**
- A component's "type" is its **definition identity**: the `Component`
  definition token, local to the process, never a persisted native address.
- Components should be defined at top level (a `val` or an `object`
  member). Static dependencies go through `Component.withDeps[D, P]`.
- In development builds, the engine diagnoses a component definition
  created inside a function that runs again: "component redefined at
  <site>; this remounts every instance".

  Updates VISION §5.2.

**R8 (Q5, Q17): reconciliation.**
- **`ForEach`.** The row function runs **once per key mount** and receives
  `Inputs[A]`, a per-key signal. It never re-runs when the value changes.
- **`Switch`.** A switch keyed by branch reconciles when the branch key
  stays the same, and remounts when it changes. A switch without keys
  compares branch values, and an unequal branch remounts.
- **`setAll` deltas.** Structure changes are applied first: removals, then
  moves in their target order, then insertions. After that, each row's
  `Inputs` is updated with any value replacement.

**R9 (Q3): focus requests are staged intents.**
- A focus request is resolved after the pass reaches `Settled`, against
  the settled topology. A request for a ref that a `Switch` attaches later
  in the same settle loop is honoured.
- If the ref never attaches, the request is dropped and a development
  diagnostic is raised.

**R10 (Q4): restoring focus.** When a popup closes, focus goes to the first
of these that applies:
1. the originator, if it is still mounted and focusable,
2. the nearest focusable ancestor of the originator in the **ownership**
   tree,
3. the window's default focus target.

"Focusable" means it is mounted, visible, and eligible for focus. Activation
eligibility does not matter (VISION §3: focus and activation are separate
properties). So a disabled button that remains focusable for screen readers
still qualifies.

**R11 (Q14): key precedence.** A key event is offered to handlers in this
order:
1. the IME composition, if one is active,
2. the focused control's own editing and text keys,
3. `.shortcut` bindings, bubbling from the focused node out through its
   ancestors,
4. window-level command chords (the menu).

A text control does not consume chords that use the primary modifier unless
it declares them. On Windows and Linux there is no native menu bar, so menu
chords live in the window's command table and are shown by an in-app menu
bar.

### Input, custom elements, animation

**R12 (Q8): pointer events and transactions.** Each delivered input event
is its own transaction, after coalescing. Coalescing happens before the
transaction, according to the source's delivery policy. An element declares
the policy for its pointer stream:
- moves default to coalesce-latest,
- an element can opt into complete-stream, for freehand drawing.

**R13 (Q15): reads in handlers versus paint.**
- **Handlers** run inside a transaction and read the staged state through
  signals. That is authoritative.
- **The snapshot parameter.** The interaction snapshot passed to a handler
  is the committed geometry, and it is used for hit testing only.
- **Paint and layout** receive a `Committed` read capability. They cannot
  see staged state.

**R14 (Q9): unplaced children.**
- A child that a custom layout never places is not rendered, not
  hit-testable, and not exposed to accessibility. It stays mounted.
- `measure` may be called more than once in one layout. Results are cached
  per constraint, and in development builds measuring with more than one
  distinct constraint in a pass raises a warning about intrinsic cost.

**R15 (Q16, awkwardness #5): animation is outside the reactive graph.**
- Animation ticks are **not** transactions.
- `scope.animate` returns `Presentation[A]`, not `Signal[A]`. A
  presentation value feeds paint, transform, and opacity properties
  directly. It cannot feed derived signals.
- Layout animation uses an explicit layout-presentation channel, and its
  cost is charged to layout.
- This also answers awkwardness #5. Custom elements get **per-phase
  inputs** (`layoutInputs`, `paintInputs`, `semanticInputs`), plus
  presentation inputs that invalidate paint only.

  Updates VISION §8.2.

**R16 (Q18): streaming results.**
- `Work` can emit through a `Progress[P]` channel with a declared delivery
  policy, which defaults to coalesce-latest.
- The detailed design belongs to C1.6a and needs a seventh corpus program
  before it is frozen.

## Decisions on the API awkwardnesses

| # | Decision |
|---|---|
| 2 | **Adopt** `Component.withDeps` and the "component redefined" diagnostic (R7). |
| 4 | **Adopt** the two-axis split with named presets (R2). |
| 1, 3 | **Adopt** explicit builder status (R3). |
| 5 | **Adopt** per-phase element inputs and `Presentation` (R15). |
| 7 | **Adopt** type-preserving modifiers: `extension [V <: View](v: V)` returns `V`. |
| 15 | **Resolved** by `attempt` (R1). |
| 18, 20, plus the review's note about `TextField` | **Adopt, as a requirement.** The public element API must grow text measurement, IME, hover and cursor, and focused-part / active-descendant support. The Stage 2 exit adds this check: `TextField` is built only on the public API. |
| All others | Each is decided when the skeleton is revised (task A-0b). That task records either an API change or a short rationale in `examples/REVIEW.md`. |
